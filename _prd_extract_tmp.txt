1. Executive Summary
The Driver Retention Module will be added to the existing XXII Century Admin Panel, where the Gross Profit module already operates. Its purpose is to identify dissatisfied drivers early, route actionable feedback to the appropriate department, give management visibility into unresolved retention risks, and combine driver sentiment with selected six-week Gross Profit performance indicators.
Target releaseDavid requested a simple live version within approximately two weeks. All features marked MVP in this document are treated as required for the first release unless the client explicitly approves a scope reduction.

1.1 Business objectives
Collect recurring driver satisfaction feedback without requiring manual outreach.
Identify any driver rating 1-3 as At Risk.
Determine whether dissatisfaction relates to Dispatch, Safety, Accounting, or Maintenance.
Notify the responsible department promptly and provide James visibility into every low-rating case.
Track the lifecycle of retention issues from Open to In Progress to Resolved.
Show rating history together with six-week operational/financial averages from Gross Profit.
Encourage satisfied drivers (4-5 stars) to leave a public Google review.

6. Issue Follow-up & Resolution
Each low-rating case must have a status that an admin can change manually: Open, In Progress, Resolved.
Admins must have a separate internal-notes function to record actions taken. Internal notes are not shown to the driver.
Previous ratings and comments must remain visible to admins as history.
The module should show rating history so management can see whether sentiment is improving or worsening.
After an issue is resolved, the system should support a special resolution follow-up survey asking the driver to rate how quickly, efficiently, and effectively the problem was resolved.
MVP treatment of resolution surveyThe client requested this capability conceptually but did not define its exact questions, timing, or rating model. The core data model should support it. Final copy and trigger timing can be approved during UI/UX review or treated as a controlled post-MVP enhancement if the two-week deadline is at risk.

8. Gross Profit Integration
The retention module must reuse the driver identity already used by XXII Admin/Gross Profit wherever possible rather than create a duplicate driver identity.
Each driver retention record must be associated with the correct Gross Profit driver record.
The UI must show 6-week averages for miles/week, driver payroll, and gross margin.
Driver CPM should be shown only if the team confirms a reliable existing source for this value.
Gross Profit values should be read from the existing application/data source rather than manually duplicated wherever technically practical.
DependencyThe source/mapping for driver phone number and CPM still needs to be confirmed during development discovery. This should not block UI construction, database modeling, or the core retention workflow.

9. Messaging Integration
Dialpad is no longer considered a viable provider for this use case. Mantas reported that using it for recurring survey outreach could risk the account being treated as spam. The implementation must therefore use an alternative SMS provider.
Provider
Current position
Twilio
Candidate. Official Twilio documentation supports outbound messaging status callbacks and incoming-message webhooks, making it technically suitable for a two-way integration pattern. Final account/compliance setup must still be validated by the developers.
SimpleTexting
Candidate raised by Mantas. Mantas reported character/content limitations and required unsubscribe handling. Capabilities must be validated before selection.
Dialpad
Excluded from the planned implementation based on client feedback.
Recommended approval wordingApprove the product requirements independently of the SMS vendor. Authorize the development team to perform a short provider validation and select Twilio or SimpleTexting based on API capability, compliance requirements, cost, delivery tracking, inbound response support, and implementation time. The module should use a provider abstraction so business logic is not tightly coupled to one vendor.

9.1 Messaging behavior required from whichever provider is selected
Send scheduled outbound survey messages.
Send up to three follow-up reminders for non-response.
Support a secure survey link or equivalent response mechanism.
Track send/delivery status where the provider supports it.
Respect opt-out/unsubscribe requirements and suppress future automated surveys for opted-out numbers.
Associate the outbound message/survey with the correct driver.
Support production-safe credentials and webhook/callback security where applicable.
10. Recommended Survey Interaction
For the two-week MVP, the cleanest product flow is to use SMS primarily as the outreach channel and send each driver a unique mobile-friendly survey link. The survey itself is hosted by the XXII application. This keeps the 1-5 rating, department ratings, required comments, Google review branch, and future UI changes under XXII's control rather than depending on SMS message formatting.
System selects an eligible driver and creates a survey occurrence with a unique secure token.
SMS provider sends the driver a short message containing the survey link.
Driver opens the mobile survey page and submits the overall 1-5 rating.
For 4-5, store response and show thank-you + Google review action.
For 1-3, collect four department ratings and required comments, then submit.
Backend stores results, marks At Risk, creates/updates the case, and sends notifications.
XXII Admin immediately reflects the new response and case state.
Why this is a product recommendation, not an already-approved client ruleThe questionnaire defines the business behavior but leaves the technical response mechanism unanswered. This link-based flow is the recommended implementation baseline for approval because it is provider-neutral and supports the required UI cleanly.

13. Roles & Permissions
Only authenticated XXII Admin users should access retention data.
Drivers access only their unique survey experience; they must not be able to view admin data or another driver's survey.
Internal notes are admin-only.
Manual survey sending and case-status changes should be restricted to authorized admin roles.
Existing XXII Admin authentication/authorization should be reused where possible.
14. MVP Acceptance Criteria
AC-01: Eligible active drivers can be scheduled according to tenure/type rules and sends are staggered.
AC-02: New drivers are not surveyed before 7 days.
AC-03: Inactive/terminated drivers are excluded.
AC-04: Admin can manually send a survey.
AC-05: System can send survey outreach using the selected SMS provider.
AC-06: Non-responders can receive up to 3 follow-ups and are visibly flagged afterward.
AC-07: Driver can submit an overall 1-5 rating from a mobile-friendly flow.
AC-08: 4-5 ratings are stored and lead immediately to thank-you + Google review request.
AC-09: 1-3 ratings mark driver At Risk and require ratings for all four departments.
AC-10: Low-rating flow captures required comments and supports separate comments for departments rated <=3.
AC-11: Configured department recipients receive immediate relevant alerts; James receives every 1-3 overall alert.
AC-12: Admin overview shows At Risk drivers and current case status.
AC-13: Admin can change case status Open/In Progress/Resolved and add internal notes.
AC-14: Driver detail shows rating history and the three confirmed 6-week Gross Profit averages.
AC-15: Previous ratings/comments are visible to admins.
AC-16: Opted-out drivers are not sent future automated survey messages once provider opt-out state is received/known.
